# Rule Improvement Candidate Draft Contract

## 1. Purpose

`rule_improvement_candidate_draft.json` is the first reviewable candidate draft
artifact after `rule_improvement_candidate_generation_input.json`.

It proposes candidate work items for later human review. It does not apply rule
changes, approve candidates, promote candidates, update prompts, or mutate SOC
pipeline state.

The artifact contract is implemented by
`schemas/rule_improvement_candidate_draft.schema.json`, with focused schema
tests in `tests/test_rule_improvement_candidate_draft_schema.py`.

## 2. Flow position

```text
rule_improvement_signal_classification.json
  ↓ export eligible human-reviewed signals
rule_improvement_candidate_generation_input.json
  ↓ scripts/generate_rule_improvement_candidate_draft.py
rule_improvement_candidate_draft.json          (reviewable draft only)
  ↓ scripts/export_rule_improvement_candidate_review_handoff.py
rule_improvement_candidate_review_worksheet.md
rule_improvement_candidate_review_decisions_template.json
  ↓ human-authored completed candidate review decisions
rule_improvement_candidate_review_decisions.json
  ↓ scripts/export_rule_improvement_candidate_creation_input.py
rule_improvement_candidate_creation_input.json (later workflow input only)
  ↓ future candidate-creation workflow
rule_candidates.yaml / prompt_candidates.yaml  (not created by this contract)
```

Candidate drafts exist before `rule_candidates.yaml` and
`prompt_candidates.yaml` so reviewers can inspect proposed work items while they
are still non-applying, non-promoting, and provenance-preserving.

The repository also has existing comparison-harness candidate artifacts:
`rule_candidates.yaml`, `prompt_candidates.yaml`, and
`promotion_recommendation.yaml`. They are not generated by this AI-assisted
post-action contract. `rule_improvement_candidate_creation_input.json` is only
later workflow input; a future bridge to concrete candidate artifacts must be a
separate reviewed workflow and must not imply apply, approval, deployment, or
promotion.

## 3. Source of authority

Candidate-draft generation must use only
`rule_improvement_candidate_generation_input.json` as its human-reviewed
decision source.

The generator must not infer eligibility from:

- AI review drafts
- AI draft comparison output
- `human_review_packet_ja.md`
- worksheets
- untranslated or translated prose notes
- raw post-action evidence without the human classification path

Japanese review packets, Japanese candidate-review worksheet rewrites, and AI
suggestions remain advisory only. They must not be used as decision sources for
eligibility, approval, candidate creation, deployment, or promotion.

The schema-defined draft artifact has this minimal shape:

```json
{
  "artifact_type": "rule_improvement_candidate_draft",
  "draft_id": "ri-candidate-draft-001",
  "source_candidate_generation_input_ref": "data/runs/run-001/rule_improvement_candidate_generation_input.json",
  "source_classification_ref": "data/runs/run-001/rule_improvement_signal_classification.json",
  "source_review_input_ref": "data/runs/run-001/rule_improvement_review_input.json",
  "candidate_generation_started": true,
  "promotion_allowed": false,
  "requires_human_approval": true,
  "candidates": [
    {
      "candidate_id": "ri-candidate-001",
      "candidate_type": "detection_rule_candidate",
      "source_signal_ref": "/supporting_signals/0",
      "source_label": "detection_gap",
      "summary": "Add detection coverage for suspicious /tmp script execution.",
      "rationale": "Human classification marked this signal as detection_gap and candidate-generation eligible.",
      "proposed_change": {
        "target": "detection_rule",

      },

        "forensics/mock/Linux.ProcessList.json"
      ],
      "source_fact_ids": [
        "process-candidate-input-001"

        "ProcessList is point-in-time evidence and does not prove full execution chain."

      "auto_apply_allowed": false,

    }
  ]
}
```

## 5. Candidate types

The first contract supports these candidate types:

- `detection_rule_candidate`
- `parser_candidate`
- `telemetry_candidate`
- `correlation_candidate`
- `prompt_candidate`

The candidate type describes the review area. It is not an instruction to
change production rules, parser code, telemetry collection, correlation logic,
or prompts.

## 6. Safety invariants

The root artifact requires:

```json
{
  "artifact_type": "rule_improvement_candidate_draft",
  "candidate_generation_started": true,
  "promotion_allowed": false,
  "requires_human_approval": true
}
```

Each candidate requires:

```json
{
  "human_review_required": true,
  "auto_apply_allowed": false,
  "promotion_recommendation_allowed": false
}
```

These flags are review gates. They must not be overridden by a generator.

## 7. Provenance requirements

Each candidate must preserve:

- `source_signal_ref`
- exact English `source_label`
- `source_fact_ids`
- `required_evidence_refs`
- rationale from the candidate-generation input context
- limitations that prevent overclaiming

Labels and refs must remain exact and untranslated. Missing or weak evidence
must remain a limitation, not a host-clean, benign, or non-execution conclusion.

## 8. Hard boundaries

This contract must not create or update:

- `rule_candidates.yaml`
- `prompt_candidates.yaml`
- `promotion_recommendation.yaml`
- detection rules
- prompts
- parser code
- telemetry collection behavior
- correlation logic

It must not mutate:

- `case.json`
- `action_result.json`
- pre-case `investigation_result.json`
- `post_action_dfir_investigation_result.json`
- containment or approval state
- verdict, severity, or confidence
- Rule Improvement promotion state

Candidate draft is not candidate approval, not a promotion recommendation, and
not deployment.

## 9. Review policy

A candidate draft may be rendered into a review worksheet and an incomplete
decisions template. Human-completed candidate review decisions may then be
validated into `rule_improvement_candidate_review_decisions.json`, and accepted
decisions may be projected into `rule_improvement_candidate_creation_input.json`.
That creation input is still not a candidate artifact, approval, deployment, or
promotion. Any later candidate-creation workflow must perform its own validation
and preserve the distinction between draft work, candidate creation, candidate
approval, regression validation, deployment, and promotion. The future workflow
boundary is documented in
`docs/design/rule-improvement/rule_improvement_candidate_creation_workflow.md`.
