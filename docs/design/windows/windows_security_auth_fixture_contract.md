# Windows Security Authentication Fixture Contract

Evidence scope: sanitized source fixtures and schema validation for one Windows
Security Event ID 4624 successful network logon and one Event ID 4625 failed
network logon. See the [Main Roadmap](../../roadmap/roadmap.md) for overall
Windows and common-pipeline status.

## 1. Purpose

This contract introduces the next standalone Windows telemetry source family
after Sysmon Event ID 1:

```text
sanitized Windows Security provider-like fixture
  -> separately reviewed source parser
  -> separately reviewed source-specific parsed event
  -> separately reviewed normalized endpoint mapper
  -> future deterministic detection and common pipeline
```

This contract owns only the first arrow's input boundary. The separately
reviewed parser and parsed-event behavior are defined in the
[Windows Security Authentication Parser Contract](windows_security_auth_parser_contract.md).
Normalized mapping is defined in the separate
[Windows Security Authentication Normalized Mapper Contract](windows_security_auth_normalized_mapper_contract.md).
Detection and downstream behavior remain later work.

Event ID 4624 means an account was successfully logged on. Event ID 4625 means
an account failed to log on. The source observations do not by themselves state
that activity was malicious, that an attacker succeeded, or that an Incident
must be created.

## 2. Why This Source Precedes Sysmon Event ID 3

The existing Windows MVP contract already names Security Event IDs 4624 and
4625 as its secondary source family, while Sysmon Event ID 3 remains a future
candidate. The canonical endpoint vocabulary also already contains
`auth_success` and `auth_failure`.

This source family adds authentication semantics rather than another process
event. It therefore tests whether the fixed common boundary can expand without
adding Windows-specific downstream contracts. That downstream validation is
not part of this fixture PR.

## 3. Fixture Cases

| Case | Fixture ID | Source observation |
|---|---|---|
| A | `windows-security-4624-network-logon-success-001` | One synthetic Logon Type 3 success from a documentation-only source address |
| B | `windows-security-4625-network-logon-failure-001` | One synthetic Logon Type 3 failure with status and substatus retained as source evidence |

Both fixtures use synthetic hosts, users, identifiers, timestamps, and the
IANA documentation address `198.51.100.24`. They are curated provider-like JSON,
not raw EVTX, exported XML, a Wazuh document, or runtime evidence.

## 4. Source Shape

The schema authority is
[`windows_security_auth_source_fixture.schema.json`](../../../schemas/windows_security_auth_source_fixture.schema.json).
The root fields are:

```text
fixture_contract_version
fixture_id
source_format
system
event_data
```

The fixed route is:

```text
provider_name: Microsoft-Windows-Security-Auditing
provider_event_id: 4624 or 4625
channel: Security
source_format: windows_security_eventlog_json
```

The reviewed common EventData fields retain subject identity, target identity,
logon type, authentication process/package, workstation, source address, and
source port. Event-specific fields are conditional:

- Event ID 4624 requires `TargetLogonId`.
- Event ID 4625 requires `FailureReason`, `Status`, and `SubStatus`.

Fields not explicitly reviewed fail schema validation. Source sentinels such as
`-` remain source values; their reviewed omission policy belongs to the
separate parser contract.

## 5. Identity And Evidence Boundaries

The following identities remain distinct:

| Identity | Authority |
|---|---|
| `provider_event_id` | Windows Security event type: 4624 or 4625 |
| `event_record_id` | Windows Event Log record identity represented by the fixture |
| `SubjectLogonId` | Source account/session identity that reported the event |
| `TargetLogonId` | Successful target logon session identity; present only in the 4624 fixture |
| `fixture_id` | Repository test-case identity only |
| canonical `event_id` | Generated by the separate normalized mapper; absent from this fixture contract |

The 4625 status values are retained as provider evidence, not converted into a
verdict or explanation by this slice. The source fixture contains no canonical
event type, detection label, severity, confidence, Incident, response, or
expected downstream result.

## 6. Done Criteria

This fixture boundary is complete when:

- exactly one reviewed 4624 success and one reviewed 4625 failure fixture exist;
- both fixtures validate against Draft 2020-12 with format checking;
- provider, Event ID, channel, identity, and event-specific required fields fail
  closed when invalid;
- filenames equal fixture IDs and fixture/event-record identities are distinct;
- unreviewed fields are rejected;
- fixtures contain no runtime lab address or downstream conclusion; and
- formatter, lint, focused tests, full tests, and whitespace checks pass.

## 7. Does Not Establish

This fixture boundary does not itself establish:

- parser or parsed-event behavior, which is owned by the separate parser
  contract;
- normalized mapping parity, which is owned by the separate mapper contract;
- deterministic detection, correlation, Incident, Triage, or Investigation;
- Wazuh field mapping, query support, or live retrieval;
- native Windows collection or fixture parity;
- account compromise, credential validity, attack success, or user intent;
- Active Directory or Domain Controller coverage; or
- live cross-platform pipeline behavior.
